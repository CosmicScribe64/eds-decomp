# Unit code_08009A68

`0x08009A68`–`0x0800AB07`, Thumb, `old_agbcc -O2`. Source: `src/code_08009A68.c`.
Helpers over the per-player duel state `gDuelPlayers[2]` (0xD64 bytes each, see [[card-table]] for the card word): remove/find/count cards in the hand (`+0x684`), the `+0x904` list and the `+0xB84` list, plus zone-link queries.

Unit status: `unit bytes MATCH` (verified with `tools/check.py code_08009A68`, 2026-09-30). A later cleanup pass applied two score-0 permuter results (`RemoveBanishedCardAt`, `FindNonFieldMagicInHand`), raising the C count to 25/29. A continuation pass then matched
`AddCardToHand`; with `IsCardInGraveyard` (2026-10-01) and `HasZoneCardEffectLink` (workflow wave 1, 2026-10-01) the unit reached 28/29. Now **29/29 functions in C** after workflow wave 3 (2026-10-02: `0x0800A78C` in wave 3); none stay `INCLUDE_ASM`, and the full `0x10A0` unit bytes remain exact.

Header migration (2026-09-30): the unit now `#include "duel.h"` and uses the canonical `struct DuelCard` / `DuelZone` / `DuelPlayer` / `DuelZonesPlayer` and the `gDuelPlayers` / `gDuelZones` externs from `include/duel.h`. Its four local struct definitions and both local extern declarations were removed; field uses were renamed (`count904` to `graveCount`, `list904` to `graveyard`, `unk91` to `unk8C[5]`, `unk12` to `owner`). `main.h` is not needed (`gMain` is not referenced). One unit-local view is kept (see Data): `struct DuelPlayerUnk9` for `IsHandRevealed`.

## Data

- `gDuelPlayers[2]` per-player state, `struct DuelPlayer` from `include/duel.h`: +0x2 `handCount`, +0x3 `deckCount`, +0x4 `graveCount`, +0x5 `fusionCount`, +0x6 `countB84`, +0x9 bit 0 flag (read by `IsHandRevealed`), +0x28 `zones[11]` (11 x 0x94), +0x684 `hand[80]`, +0x7C4 `deck[80]`, +0x904 `graveyard[80]`, +0xA44 `fusionDeck[80]` (hypothesis), +0xB84 `listB84[80]`, +0xCC4 `u16 arrCC4[80]` parallel to listB84 (`RemoveBanishedCardAt` shifts both).
- Unit-local view kept: `struct DuelPlayerUnk9` with `extern struct DuelPlayerUnk9 gUnk_020192E4_u9[2] asm("gDuelPlayers")`. Canonical `DuelPlayer` declares +0x9 as a plain `u8 unk9`; `IsHandRevealed` reads bit 0 and the ROM emits `lsl #31`, while `unk9 & 1` emits `and #1` and shifts register allocation. The view restores the 1-bit field and pads to 0xD64 so `[player & 1]` strides correctly. `DUEL_FLAGS` also uses this view symbol so the base pointer stays CSE'd in a register across the function.
- Zone (0x94 bytes, `struct DuelZone` from `include/duel.h`): +0x00 card word, +0x0A `u16 links[32]` (low byte player, high byte zone; for kind 3 the link is a card ID), +0x4A `u16 linkKinds[32]` (low byte = kind: 1/2/10 = link to another zone's card, 3 = card ID, 5 = counted by `CountZoneEquips`/`FindAbsorbedMonsterLink`), +0x8A `numLinks`, +0x91 (canonical `unk8C[5]`) bit 3 flag (disqualifies a linked card in `CountActiveZoneLinksFromCard`/`CountZoneLinksFromCard`; hypothesis: negated/disabled).
- `gDuelZones` = the zones addressed from their own base (player + 0x28).
- Byte `0x020192E4 + 0x1B0E` (= `0x020192E0 + 0x1B12`, `flags1B12` in `code_0800C894`): bit 1 compared with a player number in `IsHandRevealed` (hypothesis: whose turn / host side).
- `struct CardRef` (0x14 bytes, argument of `EffectEquipTargetCheck`): +0 card ID, +2 bit 0 player, +2 bits 4-9 zone.
- Card numbers used here (roles unknown): 1093, 1121, 1152 (`IsHandRevealed`), 1178 (`CountAquaChorusBoosts`), 348, 1058, 1244 (`CountZoneLinksFromCard`), 1910-1912 (card subtype special cases).

## Matching tricks

- `RemoveBanishedCardAt`: permuter score-0 fix. A no-op `i++; i--;` pair after the count decrement shifts the loop-index copy's scheduling (`/* FAKEMATCH */`).
- `FindNonFieldMagicInHand`: permuter score-0 fix. Hold the `0x7FF` mask in a local `u32 mask` inside the loop and index the stats table through it, so the literal load lands one instruction later (`/* FAKEMATCH */`).
> [!warning] Contradiction
> The next bullet (2026-09-30) says a `u8`/`& 0xFF` form of the linked-zone player "doesn't produce the ROM's `lsl #24; lsr #24`", so `int lp = (u8)link;` is required. The wave 3 match of `CountZoneLinksFromCard` (2026-10-01, `build/wf/CountZoneLinksFromCard/NOTES.md`) needs `u8 lp = link;`: its extra pre-loop RTL keeps loop.c's first pass from strength-reducing `linkKinds[i]`. Resolved in favour of the matched source: `int lp = (u8)link` is right for `CountActiveZoneLinksFromCard` and its siblings, `u8 lp` for `CountZoneLinksFromCard`; neither form is wrong in general.

- Zone access: `#define ZB(p, z) ((struct DuelZone *)((u8 *)gDuelZones + (z) * 0x94 + (p) * 0xD64))`, called as `ZB(player & 1, zone)->field` at **every** use (no zone-pointer local). This is what makes `CountZoneEquips`, `CountActiveZoneLinksFromCard`, `FindZoneLinkFromCard`, `DestroyInvalidEquips` match. The linked zone is `ZB(lp & 1, link >> 8)` with `int lp = (u8)link;` (a `u8`/`& 0xFF` form doesn't produce the ROM's `lsl #24; lsr #24`), and in `DestroyInvalidEquips` the zone byte must be a `u16` local.
- `FindAbsorbedMonsterLink` is the exception: `player &= 1;` then a `z` pointer from the same byte arithmetic with the sum parenthesised `(zone * 0x94 + player * 0xD64)`.
- Card numbers: `CARD_NUMBER(id)` through the constant pointer `((const u16 *)0x08622AB4)` when the ROM reloads the table in the loop and hoists `0x7FF` (`FindZoneLinkFromCard`); the extern array `gCardIdToNumber[]` when the ROM hoists the table (`CountActiveZoneLinksFromCard`, `CountGraveyardCardsByNumber`, `CountHandCardsByNumber`).
- Hold a card ID in a `u16` local (`u16 id = CARD_ID(word)`), otherwise it's copied to a second register (`FindTrapInHand`).
- Magic/Trap subtype as an inline `switch (type) { case 21: case 22: return (stats & 0xE0000) >> 17; default: return 0; }` (gives the `cmp #22; bgt; cmp #21; blt` tree), used as `if (!flag || GetMagicSubtype(id) == 3) ok = 1;`.
- `GetCardSubtype` inline from `code_08006878` (1910 gives 3, 1911/1912 give 1, Magic 7, Trap 8, Ticket 9, else kind) reproduces `AddCardToHand`'s control flow. An empty input constraint on `card` with an r3 clobber keeps the card pointer in r4 and the hand-offset scratch in r3; it emits no instructions and preserves the original ABI (`FAKEMATCH`).
- A byte bitfield in a struct of exactly 4 bytes is read with `ldr`; pad the struct beyond 4 bytes to get `ldrb` (`DUEL_FLAGS`).
- `EffectEquipTargetCheck` must be declared returning `int` here (the ROM tests `r0` without narrowing).

- `GetGraveyardCardById`: an inline `u16 GetList904CardId(int player, int idx)` with a local card pointer preserves the per-iteration address calculation.
- `RemoveCardFromHand` / `CompactHand`: reading through an inline `u32 GetHandCardWord(int player, int idx)` with a local card pointer retains the outer `i * 4` induction value for the inlined removal loop; a direct word expression fully strength-reduces the outer pointer.
- `ClearHandCardAt`: load `handCount` into an `int` local before declaring the slot pointer; this gives the ROM's base-before-mask load order and register allocation.
- `CountGraveyardMonsters` / `CountHandMonsters`: an inline `int GetCardType(u16 id)` wrapper plus an unsigned cast at the comparison keeps the stats-table address load inside the loop. A direct macro or a local ID hoists it; a signed comparison gives `bgt` instead of `bhi`.

## Kind-3 link scan matched (wave 1, 2026-10-01)

`HasZoneCardEffectLink` (0x78, start score 34) matches in ordinary C. Working notes: `build/wf/HasZoneCardEffectLink/NOTES.md`.

- Keep `ZB(player & 1, zone)->numLinks` in the loop condition, and build the body's zone pointer from a separate player-pointer statement:

      struct DuelZonesPlayer *pl = &gDuelZones[player & 1];
      struct DuelZone *z = &pl->zones[zone];

  Equivalent forms that also match: `u8 *pb = (u8 *)&gDuelZones[player & 1]`, or `u32 pb = P + (u32)base` followed by `pb + zone * 0x94`. Each makes the body's RTL `(plus (plus P B) Z)`. The loop.c giv add value then becomes `((P+0x4A)+B)+Z`, which emits `base+0x4A` first, as in the ROM.
- Why the single-expression forms fail: `fold()` reassociates the constant symbol out of an inline sum, whatever the term order (`Z + (P + B)` or `P + (Z + B)`). The `ZONE()` array form, a hoisted `numLinks` local, and `ZONE()` for the count also fail, and most of them lose the count hoist. The body's base copy has to move in loop pass 1; otherwise the base pseudo counts as used before it is set and the count chain stays in the loop.
- General idiom: when the ROM forms a zone address as `(playerOff + base) + zoneOff`, use a separate player-pointer statement. See [[matching-tricks]].
