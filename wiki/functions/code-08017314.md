# Unit code_08017314

`0x08017314`–`0x080184D7`, Thumb, `old_agbcc -O2`. Source: `src/code_08017314.c`.
Duel field-zone helpers that walk a zone's **link list** (see [[code-08008a1c]] for the zone struct) and queue duel
events through `sub_0801EC58` (`DuelCmd_Push`, [[code-0801e260]]). Two near-identical "monster placed in zone" handlers
(`0x08017FF4`, `0x08018280`) fire per-card on-summon effects. Related: [[code-080184d8]] (`sub_08018544` = remove card
from zone, and `sub_08019078`), [[code-08007994]].

Unit status: `unit bytes MATCH`, **8/12** functions in C (verified with `tools/check.py code_08017314`).
The three listed loop/summon functions (`0x08017314`, `0x08017DE0`, `0x08017FF4`) are
**parked drafts** (best C under `#if 0` above each `INCLUDE_ASM`), all blocked only on `old_agbcc` register
allocation / address-materialisation, not on logic. They are queued for the background permuter (2026-09-30 pass).

## Data layout

- Zone (0x94, see [[code-08008a1c]]): +0x0A `links[32]` (`(zone << 8) | player`), +0x4A `linkInfo[32]` (low byte = kind), +0x8A `numLinks`, +0x06 bit 1 face up, +0x07 bit 5 tested before the 461/1116 effects, +0x91 bit 3 (u8 bitfield, read as `lsl #28; lsr #31`).
- Player struct (0xD64): +0x0B bit 3 set when a monster (card type ≤ 20) is summoned (hypothesis: "summoned this turn").
- Card word bit 12 (`owner`) goes into bit 31 of the `sub_0801FBCC` event word.
- Link kinds seen: 1 (control), 2, 5 (destroy with source), 6, 10.

## Matching tricks

- **`int t = player & 1;` as a separate local** fixes the "`player & 1` first, then `zone * 0x94`, then `t * 0xD64`" address order that [[code-08008a1c]] lists as unsolved: `ZONE_T(t, zone)` = `zones + (zone * 0x94 + t * 0xD64)`. It matched `0x08018280`; it only helps when `t` stays live (in `0x08017314` it gets folded away again).
- `(u8)player | ((u8)zone << 8)` gives the ROM's `lsl #24` / `lsl #24; lsr #8; orr; lsr #16` location packing; with a `u16` parameter the plain `(zone << 8) | player` does not. `(u16)(...)` cast needed when the callee takes `u32` (`sub_08042AB0`).
- Two-case `switch (kind) { case 1: case 2: }` gives the signed `cmp #2; bgt; cmp #1; blt` range test (`0x08017C48`).
- `int fp = (u8)from;` (int locals holding narrowed values) instead of `u8` locals fixed `0x08017B04`'s register allocation.
- RMW on the player byte: `u8 *pl = (u8 *)&PLAYER(player); pl[0xB] |= 8;` (a struct field or `->` access folds the offset differently).
- The remaining link loops (`0x08017314`, `0x08017DE0`) compute *both* the `links[i]` and `linkInfo[i]` addresses before any load, as `(z + 0x0A) + i*2`. Direct `z->links[i]` reads get the address shape but not the order; `&z->links[i]` pointer locals fold `z + 0x0A` differently.

The `0x08017F98` case is now solved. Leave the initial count guard as a direct
`ZONE_PTR(player, zone)->numLinks` read, then declare the preserved zone pointer
and `u16 *count` inside the guarded block. In the loop, compute `offset = i*2`,
initialize `link` to zone +0x0A, add `offset` separately, then initialize `info`
to zone +0x4A and add `offset` separately. Only then load the link player,
halfword/zone, and info byte. This gives the original entry test, counter r5,
zone r4, preserved count pointer r6, and both fully materialized addresses.
The ordinary C matches the complete 0x11C4-byte unit; no empty constraints,
register bindings, or emitted inline assembly are needed.

`0x08017D38` uses the same two-statement link/info address additions in a
forward `for` loop. Its initialized loop counter is bound to r5; no empty
constraint or emitted assembly instruction is needed. Inside the loop,
`to = (player & 1) * 0xD64` is initialized separately before deriving the zone
pointer from `zone * 0x94 + to`. This retains the ROM's multiplication order
while emitting `add r0,r4,r0` for the address sum. Merely commuting the macro
expression changes the prologue and allocation. The complete 0x11C4-byte
unit matches with both small link helpers enabled in C.

## 2026-09-30 parking pass (register-allocation findings)

All five listed functions were re-derived from the m2c drafts / previous attempts and parked; none is logic-limited.

- **The two `for`-loop register layouts are mutually exclusive with plain C, for these loop bodies.** Expressing the bound as
  `ZONE_PTR(player, zone)->numLinks` makes GCC emit the ROM's un-rotated loop (entry test + back-edge) but assigns the
  counter to `r4` and the zone pointer to `r5` (the ROM's `0x08017F98` is the reverse: counter `r5`, zone `r4`). Using a
  local `struct DuelZone *z` inverts the register assignment but makes GCC rotate the loop (unconditional `b` to a
  bottom-only test). Both shapes are one permuter fix from the ROM.
- **Keeping `&z->numLinks` in `r6`** (so the count is re-read from memory after the body's call, matching the ROM) needs a
  `u16 *numLinks = &z->numLinks;` local; with a plain `z->numLinks` GCC rematerialises `z + 0x8A` each iteration.
- **Guard + `do {} while`** (as suggested by the advisor for `0x08017F98`) does give the ROM's entry-test-plus-back-edge
  shape, but it also makes GCC strength-reduce `&z->links[i]` / `&z->linkInfo[i]` into incremented pointer registers
  (`adds r4,#2; adds r5,#2`), which the ROM does not have (it recomputes `i*2` every iteration). So that route is a dead end.
- **Pointer locals for the two field bases** (`u16 *link = &z->links[i];` etc.) fold `z + 0x0A` into the load offset
  (`ldrb r3,[r0]; ... ldrh r0,[r0]` and `[r1,#10]`) instead of materialising `z + 0x0A + i*2` in its own register.
- `0x08017FF4` (87% instruction-similar to the matching `0x08018280`): the sibling's `struct DuelCard *card` local is
  what makes the ROM spill the zone base; `0x08017FF4` instead keeps the raw `zone*0x94` / `t*0xD64` in `r9`/`r8` and
  folds the base in later, so it needs `CARD(z->card).owner` reloads, not a `card` pointer.
- **Advisor call #1** (`0x08017D38`): suggested recomputing the base inside the loop and building
  `((u16 *)(base + 0x0A))[i]` / `*((u8 *)(base + 0x4A) + i * 2)`; this still folds the offset into the load and does not
  un-rotate. **Advisor call #2** (`0x08017F98`): the guard+do-while shape above.
- No finished permuter `diff.txt` existed for this unit at the time of the pass, and no `REJECTED` file was needed.
