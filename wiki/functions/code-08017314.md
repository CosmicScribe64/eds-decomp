# Unit code_08017314

`0x08017314`–`0x080184D7`, Thumb, `old_agbcc -O2`. Source: `src/code_08017314.c`.
Duel field-zone helpers that walk a zone's **link list** (see [[code-08008a1c]] for the zone struct) and queue duel
events through `sub_0801EC58` (`DuelCmd_Push`, [[code-0801e260]]). Two near-identical "monster placed in zone" handlers
(`0x08017FF4`, `0x08018280`) fire per-card on-summon effects. Related: [[code-080184d8]] (`sub_08018544` = remove card
from zone, and `sub_08019078`), [[code-08007994]].

Unit status: `unit bytes MATCH`, **11/12 functions in C** after workflow wave 2 (2026-10-01: `0x08017FF4`, `0x08017314` and `0x08017DE0` in wave 2); 1 stays `INCLUDE_ASM` (`0x08017460`, not attempted). Before wave 2: 8/12. Verified with `tools/check.py code_08017314`.
Historical (2026-09-30 pass; `0x08017314` and `0x08017DE0` matched in wave 2): the remaining loop functions (`0x08017314`, `0x08017460`, `0x08017DE0`) were
**parked drafts** (best C under `#if 0` above each `INCLUDE_ASM`), all blocked only on `old_agbcc` register
allocation / address-materialisation, not on logic, and queued for the background permuter.

## Data layout

- Zone (0x94, see [[code-08008a1c]]): +0x0A `links[32]` (`(zone << 8) | player`), +0x4A `linkInfo[32]` (low byte = kind), +0x8A `numLinks`, +0x06 bit 1 face up, +0x07 bit 5 tested before the 461/1116 effects, +0x91 bit 3 (u8 bitfield, read as `lsl #28; lsr #31`).
- Player struct (0xD64): +0x0B bit 3 set when a monster (card type ≤ 20) is summoned (hypothesis: "summoned this turn").
- Card word bit 12 (`owner`) goes into bit 31 of the `sub_0801FBCC` event word.
- Link kinds seen: 1 (control), 2, 5 (destroy with source), 6, 10.

## Matching tricks

> [!warning] Contradiction
> The next bullet (page text from the 2026-09-30 pass) says `int t = player & 1;` does not help `0x08017314`, where it "gets folded away again". The wave 2 match (2026-10-01, `build/wf/sub_08017314/NOTES.md`) depends on it: the zone pointer is re-derived inside the loop as `ZONE_T(t, zone)` from the outer `t`, and re-deriving it with `player & 1` inline scored 36. Resolved in favour of the matched source.

- **`int t = player & 1;` as a separate local** fixes the "`player & 1` first, then `zone * 0x94`, then `t * 0xD64`" address order that [[code-08008a1c]] lists as unsolved: `ZONE_T(t, zone)` = `zones + (zone * 0x94 + t * 0xD64)`. It matched `0x08018280`; it only helps when `t` stays live (in `0x08017314` it gets folded away again).
- `(u8)player | ((u8)zone << 8)` gives the ROM's `lsl #24` / `lsl #24; lsr #8; orr; lsr #16` location packing; with a `u16` parameter the plain `(zone << 8) | player` does not. `(u16)(...)` cast needed when the callee takes `u32` (`sub_08042AB0`).
- Two-case `switch (kind) { case 1: case 2: }` gives the signed `cmp #2; bgt; cmp #1; blt` range test (`0x08017C48`).
- `int fp = (u8)from;` (int locals holding narrowed values) instead of `u8` locals fixed `0x08017B04`'s register allocation.
- RMW on the player byte: `u8 *pl = (u8 *)&PLAYER(player); pl[0xB] |= 8;` (a struct field or `->` access folds the offset differently).

> [!warning] Contradiction
> The next bullet (2026-09-30 pass) says direct `z->links[i]` reads get the address shape but not the order. The wave 2 match of `0x08017314` (2026-10-01, `build/wf/sub_08017314/NOTES.md`) uses direct `zp->links[j]` / `zp->linkInfo[j]` reads; what fixed it was the `j = i - 1` loop shape and the re-derived zone pointer. `0x08017DE0` did use the separate address additions. Resolved in favour of the matched source.

- Historical (both matched in wave 2, see below): the remaining link loops (`0x08017314`, `0x08017DE0`) compute *both* the `links[i]` and `linkInfo[i]` addresses before any load, as `(z + 0x0A) + i*2`. Direct `z->links[i]` reads get the address shape but not the order; `&z->links[i]` pointer locals fold `z + 0x0A` differently.

The `0x08017F98` case is now solved. Leave the initial count guard as a direct
`ZONE_PTR(player, zone)->numLinks` read, then declare the preserved zone pointer
and `u16 *count` inside the guarded block. In the loop, compute `offset = i*2`,
initialize `link` to zone +0x0A, add `offset` separately, then initialize `info`
to zone +0x4A and add `offset` separately. Only then load the link player,
halfword/zone, and info byte. This gives the original entry test, counter r5,
zone r4, preserved count pointer r6, and both fully materialized addresses.
The ordinary C matches the complete 0x11C4-byte unit; no empty constraints,
register bindings, or emitted inline assembly are needed.

`0x08017D38` uses the same two-statement link/info address additions in a
forward `for` loop. Its initialized loop counter is bound to r5; no empty
constraint or emitted assembly instruction is needed. Inside the loop,
`to = (player & 1) * 0xD64` is initialized separately before deriving the zone
pointer from `zone * 0x94 + to`. This retains the ROM's multiplication order
while emitting `add r0,r4,r0` for the address sum. Merely commuting the macro
expression changes the prologue and allocation. The complete 0x11C4-byte
unit matches with both small link helpers enabled in C.

## 2026-09-30 parking pass (register-allocation findings)

All five listed functions were re-derived from the m2c drafts / previous attempts and parked; none is logic-limited.

- **The two `for`-loop register layouts are mutually exclusive with plain C, for these loop bodies.** Expressing the bound as
  `ZONE_PTR(player, zone)->numLinks` makes GCC emit the ROM's un-rotated loop (entry test + back-edge) but assigns the
  counter to `r4` and the zone pointer to `r5` (the ROM's `0x08017F98` is the reverse: counter `r5`, zone `r4`). Using a
  local `struct DuelZone *z` inverts the register assignment but makes GCC rotate the loop (unconditional `b` to a
  bottom-only test). Both shapes are one permuter fix from the ROM.
- **Keeping `&z->numLinks` in `r6`** (so the count is re-read from memory after the body's call, matching the ROM) needs a
  `u16 *numLinks = &z->numLinks;` local; with a plain `z->numLinks` GCC rematerialises `z + 0x8A` each iteration.
- **Guard + `do {} while`** (as suggested by the advisor for `0x08017F98`) does give the ROM's entry-test-plus-back-edge
  shape, but it also makes GCC strength-reduce `&z->links[i]` / `&z->linkInfo[i]` into incremented pointer registers
  (`adds r4,#2; adds r5,#2`), which the ROM does not have (it recomputes `i*2` every iteration). So that route is a dead end.
- **Pointer locals for the two field bases** (`u16 *link = &z->links[i];` etc.) fold `z + 0x0A` into the load offset
  (`ldrb r3,[r0]; ... ldrh r0,[r0]` and `[r1,#10]`) instead of materialising `z + 0x0A + i*2` in its own register.
- Historical `0x08017FF4` (matched in wave 2, see below; 87% instruction-similar to the matching `0x08018280`): the sibling's `struct DuelCard *card` local is
  what makes the ROM spill the zone base; `0x08017FF4` instead keeps the raw `zone*0x94` / `t*0xD64` in `r9`/`r8` and
  folds the base in later, so it needs `CARD(z->card).owner` reloads, not a `card` pointer.
- **Advisor call #1** (`0x08017D38`): suggested recomputing the base inside the loop and building
  `((u16 *)(base + 0x0A))[i]` / `*((u8 *)(base + 0x4A) + i * 2)`; this still folds the offset into the load and does not
  un-rotate. **Advisor call #2** (`0x08017F98`): the guard+do-while shape above.
- No finished permuter `diff.txt` existed for this unit at the time of the pass, and no `REJECTED` file was needed.

## Summon event 0x93 matched (wave 2, 2026-10-01)

`sub_08017FF4` (0x28C, start score 52) matches in ordinary C. Working notes: `build/wf/sub_08017FF4/NOTES.md`.

- What differed: reload-register picks (r3 where the ROM uses r2, r1 or r0). The ROM's function-wide spill-register set is {r0, r1, r2}; ours also contained r3, because the constant-1 pseudo of the 1116 case's `player & 1` got r2 and stayed live into `owner & 1`. With r2 taken, two insns had to spill r3, and the `last_spill_reg` round robin then shifted every later reload, including the prologue's 0xD64 and the `t*0xD64` output. In the 461 and 1116 cases the ROM reloads the 1 after copying player (`adds r0,r5,#0; movs rX,#1; ands`), so its constant-1 pseudo is long-lived and spilled.
- Fix 1: the 461/1116 address uses `ZONE_PTR(player, zone)` (`t*0xD64 + z*0x94`); the `_ZP` order put the products in the wrong registers.
- Fix 2 (the key change): compute the zone pointer from `player & 1` rather than from `t`, `struct DuelZone *z = &gUnk_020192E4[player & 1].zones[zone];`. This creates a `1` pseudo in that block; CSE's jump-following paths (which start after the 1418 checks) reuse it in the 461 and 1116 cases. The pseudo crosses calls, gets no hard register and is reloaded at each use, as in the ROM (the same already happened to the 0x148 constant pseudo). r3 then drops out of the spill set and every reload register lines up.
- Lesson: when the ROM reloads a small constant in several distant blocks (copy first, then `movs rX,#k`), look for an earlier block whose source writes the same constant expression afresh. See [[matching-tricks#Register allocation priority and reload rotation]].

## Wave 2 matches (2026-10-01)

Both match in ordinary C (`sub_08017FF4` above was the first wave 2 match in this unit). Working notes: `build/wf/sub_08017314/NOTES.md`, `build/wf/sub_08017DE0/NOTES.md`.

### `sub_08017314` (0x14C, start score 71; ordinary C)

The ROM splits two values into two pseudos each: the zone pointer (r2 before the loop, copied to r8 in the preheader) and the loop counter (r0 at the head, copied to ip after the loads and back with `mov r0, ip` before the bottom test); `z + 0x4A` is hoisted and spilled to `[sp]`. With a plain `int i` the counter stays in one low register and jump2 cross-jumps the bottom test into the top one, so the loop is no longer rotated (144).

1. Loop shape: `for (i = z->numLinks; i > 0; i--) { j = i - 1; ... index with j ... }`. GCSE replaces the bottom `i = i - 1` with a copy from the `j` computation, so `i` is not a biv (no strength reduction), and the ROM's ip copy and `mov r0, ip; cmp; bgt` appear.
2. Zone split: re-derive the zone pointer inside the loop, `struct DuelZone *zp = ZONE_T(t, zone);`, with `int t = player & 1;` kept as a local. GCSE turns it into a copy of the outer `z` and loop.c hoists the copy into the preheader (`mov r8, r2`); this also hoists and spills `zp + 0x4A` and spills `player` (160 -> 4).
3. Inner zone: `int lt = lp & 1; lzp = ZONE_T(lt, lz);` computes `lp & 1` before `lz * 0x94` (`ZONE_PTR_ZP` was 4 lines off).

Failed: `while (--i >= 0)`, `i-- > 0`, `for (i = n - 1; i >= 0; i--)` (no duplicated exit test, ~133); indexing by `(i - 1)` (fold gives `i*2 - 2`, strength-reduced); `j = i - 1; ...; i = j;` (146); `zp = z` in the loop (cprop removes it, 174); `player & 1` inline instead of `t` (36). The NOTES also record a helper-script name clash in the shared scratchpad with another agent's helper (no code leaked into the other function); the NOTES recommend keeping per-function helpers under `build/wf/<func>/`.

### `sub_08017DE0` (0x1B8, start score 102; ordinary C)

Steps (score after each):

1. 74: a zone pointer local `zp` and the two-statement address additions before the loads (`offset = i * 2; link = zp + 0xA; link += offset; info = zp + 0x4A; info += offset;`), the idiom of `0x08017F98` / `0x08017D38` above. `i*2` no longer stays live and `i` is no longer spilled.
2. 24: reuse `i` as the outer counter of the second (`sub_08017D38`) loop. The ROM's outer player counter is in r7, `i`'s register; merging gives `i` 20 refs, which outranks the base pointer (ip) in global-alloc.
3. 18: `int t = player & 1; zp = ZONE_T(t, zone);` gives the body's `and; zone*0x94; t*0xD64` order.
4. 0: `lp = (u8)*link;` instead of `*(u8 *)link`. The last diff was zone (r8) and the `0xD64` constant (r9) swapped: the `0xD64` pseudo has two REG_EQUIV constant sets, so its live length counts x4 (156 vs zone 162, both 10 refs). The `(u8)` of the halfword adds 2 pre-combine insns inside `0xD64`'s live range (+8 for it, +2 for zone): 164 vs 164, and the tie goes to the lower pseudo (zone). Combine still emits `ldrb` + `ldrh`.

Failed: `ZONE_PTR_ZP` for `zp` (136), macro-direct link/info (218), `register int i asm("r7")` (r7 is the Thumb frame pointer; garbage `mov r0, sp`), s16 `lp` (38), u16/s16 `lz` (18/20), `lz` before `lp` (40); a `register int zone asm("r8")` pin reached 2.
