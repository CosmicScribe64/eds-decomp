# Unit code_0801E260

`0x0801E260`–`0x0801F453`, Thumb, `old_agbcc -O2`. Source: `src/code_0801E260.c`.
The unit holds duel-side helpers: the message-box request block at `0x02017A30`, two HBlank HOFS wave handlers, the duel BGM choice, and the duel command queue at `0x020185C0`.

Unit status: `unit bytes MATCH`, **11/12 functions in C** (verified with `tools/check.py code_0801E260`). `sub_0801E260` has a draft under `#if 0`.

## Shared headers

This unit uses the canonical shared headers instead of local definitions:
`include/main.h` (`struct Main`, `gUnk_03000040`), `include/duel.h` (via `duel_ui.h`;
`struct DuelZone`/`DuelPlayer`/`DuelState`, `gUnk_020192E0`) and `include/duel_ui.h`
(`DuelCmdEntry`/`DuelCmd`/`DuelScreen`, `gUnk_020185C0`, `gUnk_0201CFB0`).
The migration removed seven local struct definitions (`Main`, `DuelCmdEntry`, `DuelCmd`,
`DuelZone`, `DuelPlayer`, `DuelState`, `DuelScreen`) and their `extern`s.

These local views are kept. They are unit-specific tags aliased with `asm("...")`, and none
is compiled except `DuelStateView`, which `sub_0801E944` uses:

- `struct DuelStateView gUnk_020192E0View asm("gUnk_020192E0")`: canonical
  `struct DuelState` stops at `phaseStep` +0x1B20, but `sub_0801E944` also clears
  +0x1B21 and the `sub_0801E260` draft uses +0x1B16, `selCard` +0x1B28 and `sel`
  +0x1B2C. Fields `unk1B12_2` (canonical `phase1B12`) and `unk1B20` (canonical
  `phaseStep`) map by offset.
- `struct DuelPlayerView` (inside `DuelStateView`): canonical `struct DuelPlayer`
  names +0x08/+0x09 `unk8`/`unk9`; the draft reads flags at +0x08 bit 4 and +0x09
  bit 5 (`flag8_4`/`flag9_5`).
- `struct SelMask`: menu state at +0x1B2C, not covered by the canonical header.
- `struct ZoneWord`: the draft reads the zone word's flag at bit 18, while canonical
  `struct DuelCard` puts `flag20` at bit 20.

`gUnk_0201CFB0.busy` (canonical, `u16` bit 3) and `gUnk_020185C0.running`
(canonical, `u32` bit 13) compiled byte-identically to the old `u8` bitfields, so no
local views were needed there.

## Data

- `0x02017A30` message request block: `+0x0` handler (`u16 (*)(void)`), `+0x4` u16 id (bits 0-14) and flag (bit 15), `+0x6` u16 arg (set by the command handlers in [[code-080162c4]]), `+0xA` step index, `+0xB` state, `+0xC`, `+0xD`.
- `0x020185C0` duel command block: `+0x0` current command (8 bytes), `+0x8` queue of 256 × `{u16 cmd, arg2, arg4, arg6}`, `+0x808` u16 count, `+0x80D` bit 5 `running`, `+0x810` `u16 *` HOFS wave table. The map from command id to handler is the jump table of `sub_0801ECA8` (table at `0x0801ECEC`).
- `gUnk_08198F20`: 24 × `{u16 opponent, u16 bgm}`.

## Matching tricks

- `sub_0801ECA8` was generated mechanically from the jump table (one `case` group per target label, in label address order) and matched first time.
- `sub_0801E260` draft notes: the case bodies are laid out in the order 1-5, 11, 12, 10, 6, 7, 8, 9 (source order). The ROM tests zone `+6` bit 1 with `ldrb [#6]; and #2`, which a scratch compile reproduces only through a zone pointer local (`struct DuelZone *z = &...zones[10]; if (!z->flag6_1)`). It also keeps an explicit `& 1` on the player bit (`and` with a register holding 1), which a direct 1-bit field read folds away. This is unresolved.

- `sub_0801E998`: the id test is `switch (id) { case 1: case 5: ... }` (reads the stored bitfield back with `lsl #17; lsr #17`); `if (id == 1 || id == 5)` gives an `and` with a kept `0x7FFF`.
- `sub_0801EA7C`: `StepFunc f = gMsg.func; if (f != NULL) return f(); return 0;` gives the ROM's `return 0` first layout; the `if (f == NULL) return 0;` form is laid out the other way round.
- `sub_0801EA9C`: a local `struct DuelMsg *msg = &gMsg` keeps the address in `r4` across the call.
- `sub_0801EBA8`: the table search is a `do { ... break; } while (++i <= 0x17);` loop; the ROM re-reads `gMain+0x4870` each iteration and does not strength-reduce the index. A `for` loop hoists the read.

A follow-up tested eight combinations of u16/u32 selection-state, substate and zone containers. All keep the private 0x6C0 size, against the target's 0x6E4. Fixed-address card-number/stats lookups change allocation but do not match (best normalized gap 485 instruction lines). Neither family is enabled. Evidence: `build/bigguns-lead2/menu_execute.py` and the private `solo-fixed-stats-*` checks.

## Hand-scan message interface (2026-10-01)

`sub_0801EC58` keeps u16 parameters for the first two arguments and explicitly decodes word parameters 3 and 4 into u16 locals, in that order. The original entry shifts and all 0x11F4 unit bytes stay exact. This agrees with the word packing in [[code-0805a30c]], and existing callers that already narrow their values keep the same low-half meaning. The final artifact is `sub_0801EC58/solo-hand-message-clean/`, and the full-ROM run is in `build/lead-pass29/`.
