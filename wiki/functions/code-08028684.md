# code_08028684

This is a screen state machine on the work area `0x02020310` ([[code-08027580]] documents its neighbours, which use the same `struct Work20310` layout).
It looks like a hand-choice mini game, rock-paper-scissors style (hypothesis). The player picks a hand 0-2 (`hands[0].hand`), the CPU or the link partner answers (`unkABC`), and `sub_08028930` judges the pair. Link exchange goes through `sub_0807BCF4` / `sub_0807BCFC` (message ids 0x51, 0x52, 0x53).

- `+0xAAC`: hands[4] `{unk0, s8 offset (slide -4/+4), hand 0-2, unk3}`; hands[1].unk0 == 0x30 gates input in step 3
- `+0xABC`: opponent hand

## Matching tricks
- `sub_080287A4`: `(A*i - 4) - B` only matches with a dummy `s32 four = 4;` (assigned in the loop) instead of the literal 4, which the compiler reassociates into `A*i - (B + 4)`.
- `sub_08028FD0`: a local `u8 *q = &gWork.unkB1C;` gives the ROM's `mov r8, (base + 0xB1C)` hoisted at entry. Register numbering in the later blocks depends on which fields go through `w->` (r6) and which through `gWork.` (fresh constant): B1D, B16 and `hands[0].hand` use `w->`.
- Historical (matched in wave 3, see below): `sub_08028D9C` (not matched): the ROM keeps a second copy of the work pointer (r3, used only by the 0x20 branch) and does not CSE the `unkB0D` address in the second block. The build gets an extra r7. Tried `p = w` copy, all-`w`/all-`gWork.`, volatile read.
- `sub_08028930`: the final `(a,b) = (2,2)` draw uses an initialized `u8 result = 2` with an empty read/write constraint. This FAKEMATCH hint keeps its return block separate from the other two draws, reproducing both ROM `mov r0,#2` blocks without adding instructions or unset values.

### `sub_08028D9C` (0x234, start score 124; ordinary C)

The fix was choosing, access by access, between the work pointer `w` (r6) and direct `gWork.` accesses (neither all-`w` nor all-`gWork.` works):

1. Entry check `gWork.unkB0D == 0` (direct), not `w->unkB0D`. With temporaries in the entry block, jump.c's `thread_jumps` sees the same sequence as the later `if (gWork.unkB0D != 0)` and threads the entry branch straight into the link body (the ROM's `b _08028F02`). That also stops CSE reusing the second check's base in the body (it reloads `gWork` fresh) and removes the extra r7. `thread_jumps` refuses to equate user-variable pseudos, so `w->` blocks the threading.
2. Left (`0x20`) branch: `gWork.hands[0].offset` (direct). The PRE (GCSE) copy of the entry's `gWork` load gives the ROM's `add r3, r6, #0` and the r3 base there; the `0x10` branch stays direct and keeps a fresh load.
3. CPU-answer block: store `hands[1].offset = 4` before `unkB1E = 0`.

`w` stays for the A-branch accesses and the link call's `w->hands[0].hand` / `w->unkB10`.
