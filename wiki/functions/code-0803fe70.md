# Unit code_0803FE70

`0x0803FE70`-`0x08040EBB`, Thumb, `old_agbcc -O2`. Source: `src/code_0803FE70.c`. Sits after [[code-0803c838]] / `code_0803DD7C` (helper `AddEffectTarget` appends a target word to `ref->targets[numTargets++]`, and `TryAddEffectTarget(ref, player, zone)` validates and adds a chosen zone). Every function here is a **target selector** `int f(struct CardRef *ref)` for one card effect: it returns 1 when the selection is finished (targets stored in the `CardRef`, or none possible) and 0 while it waits for the player. State byte: **`0x02017A40 + 0x3E5`** (step 0 shows the prompt text with `TextBoxOpen(0x206, 0x712, 0xB, text)`, step 1 and later wait for input, and the byte resets to 0 when the B/cancel bit `gMain+6 & 2` is seen).

Unit status: `unit bytes MATCH` (0x104C bytes), **17/17 functions in C** after workflow waves 2-3 (2026-10-01: `0x08040478` in wave 2, `0x08040294` in wave 3); none stay `INCLUDE_ASM`, so the unit is complete in C. Before wave 2: 15/17, verified with `tools/check.py code_0803FE70` on 2026-09-30 after enabling `EffectRedirectTargetChainB` and `EffectTakeControlOfMachineChainB`.

## Structs and globals
- `CardRef` (see [[code-08030b88]]): `+3` byte (flags, `& 0xFC` used), `+8` u16 (`>> 8` used), `targets[3]` at `+0xC`.
- Cursor of the duel screen `gDuelScreen`: `+0x824` is the player and `+0x828` plus `+0x82C` give the zone (row and column). Every selector uses them.
- `gDuel + 0x1B64` u16 / `+0x1B66` u16: results of the last prompt (`DuelPrompt_Post`).
- `0x03000040 + 6` (u16): input flags, bit 1 = cancel; `+0x4872` u16: text-entry result.
- Selector step byte `0x02017A40 + 0x3E5`; `0x3E6` / `0x3E7` cleared by `0x080408B4`.
- `GetZoneCardType(player, zone)` returns a small monster attribute/class (compared with 7); `gCardNames[n]` holds 0x40-byte card names.

## Matching tricks
Most of these apply to every selector of this family. See also [[code-08040ebc]].
- **`u8 *es = gChain; u8 *st = es + 0x3E5;`** gives the unfolded `ldr; ldr; adds` step pointer. A direct `gChain[0x3E5]++` (statement, not `&x[..]`) also gives the pair form and is what the ROM uses when the pointer must not live across a call (`0x080408B4`: every case re-materialises it; `0x0803FE70`).
> [!warning] Contradiction
> The next bullet (from the earlier selector matches `0x08040B14`, `0x080409E0`, `0x080408B4`) prescribes `(*st)++; return 0;` in every case and no `goto`. The wave 3 match of `0x08040294` (2026-10-01, `build/wf/EffectTailorOfTheFickleChainB/NOTES.md`) needed case 3's success path to end with `(*st)++; goto out3;` (label before case 3's own `return 0`): with `(*st)++; return 0;` there, case 0's increment merged into case 3's, the reverse of the ROM. A `goto inc` into case 0 also matched. Resolved in favour of the matched source: the per-case tail is the default, but a `goto` may be needed to set the cross-jump direction.

- **Write the shared `(*st)++; return 0;` tail into every case (no `goto inc`).** gcc's cross-jumping then merges the tails exactly like the ROM (which block survives, whether the text calls `TextBoxOpen(0x206, 0x712, 0xB, X)` get merged, and which of ref/st gets r4 vs r5 all follow from this; with `goto` the register priorities came out swapped). Matched `0x08040B14`, `0x080409E0`, `0x080408B4`; a case that never increments (returns 1) changes which tail survives.
- **`int z = 0;` (declared inside the cancel block, after any pointer) and `*st = z; return z;`** reproduces `movs r0,#0; strb r0,[st]; b end`; the other `return 0`s stay plain.
- **Target word `(u8)p | (u8)zn << 8` in this operand order, stored in a `u16 w`** (`0x080409E0`, `0x08040FB0` in the next unit); `(u8)zn << 8 | (u8)p` schedules the shifts differently. For the `((1 - p) << 24 >> 8 | (u32)zn << 24) >> 16` form the extra parentheses around `((u32)zn << 24)` matter (`0x08040110`).
- **`u32 p = w824;` declared before `int zn = w828 + w82C;`** makes gcc compute the address of `w824` first but load it after the sum (D00-style ordering).
- **`ZB2(pl, zn)` with `int pl = 1 & p;` first** matches the z-first multiply order in `0x08040040`.
- **`gCardNames[idx]` as `const char [][0x40]`**, and for a pointer held across calls a local `u8 *mv; ... mv = (u8 *)&gMain; r = (u16 *)(mv + 0x4872);` assigned late gives the `ldr; ldr; adds` order (`0x080408B4`).
- **Uninitialised local** (`int keys;` assigned in only two `case`s of a `switch`) reproduces a call argument left over in r2 on the default path (`0x08040110`).
- **`switch` whose `default` shares the ROM's `return 1`**: put `default: return 1;` last and let case 3 fall out of the block. gcc merges the `return 0` paths.
- **Beware stale files.** Docker sometimes compiles the previous version of a file that was just rewritten. A script that rewrites a file and immediately runs `check.py` should sleep about 1.5 s. Several false "match" and "error" results in early experiments came from this.

This reproduces the target-count bitfield update's scratch register. The compiler-only hint is marked FAKEMATCH in source and emits no instructions.
- `EffectTakeControlOfMachineChainB`, Thumb, `0x138` bytes, matching C. An empty input constraint on the shifted player bit keeps that load before the zone-index multiplication. Returning the same local zero stored during cancellation branches directly to the epilogue. Both compiler constraints are marked FAKEMATCH and emit no instructions.

The compiler hints emit no instructions. Each conversion passed a whole-unit byte comparison with the baserom; remaining assembly functions retain their original bytes. Earlier notes describing these functions as allocation near misses are resolved by the matching C above.

## `EffectRedirectTargetChainB` dispatch restriction (verified 2026-09-30)

The ROM sets its input-key mask only for card numbers `0x431` and `0x525`; the other switch path passes the existing `r2` value to `DuelCursor_PickTarget`. The decompiled routine preserves this existing behavior rather than adding a default value.

Scanning all 426 records (`0x18` bytes each) of the effect table at `0x0819A9D4` for selector pointer `0x08040111` in field `+0x14` found exactly two entries: record 216 at `0x0819BE14`, key `0x431`, and record 327 at `0x0819C87C`, key `0x525`. The matching `DuelLink_RunRemoteChainB` looks up the effect index using `FindCardEffect(id45C)`, loads this `+0x14` callback, and invokes it with the working and other `CardRef`. This verifies the table dispatch's card-number restriction; it does not claim every conceivable direct caller is constrained. There are no direct calls to this function in the current disassembly.

## Wave 2 matches (2026-10-01)

Working notes: `build/wf/EffectSpellTrapTargetChainB/NOTES.md`.

### `EffectSpellTrapTargetChainB` (0x16C, start score 58; FAKEMATCH)

- `j` must be `int`; the parked draft's `u16 j` added narrowing.
- Loop 1 keeps `ZB` order and reads the card into a `u16 id`. The zero-extending AND with 0xFFFF is a loop-invariant computation that uses the 0x7FF mask, so loop.c's `force_movables` credits its savings and lifetime to the mask, which is then hoisted out of the outer loop into r7 (the ROM's fourth invariant). A `u32 id` never hoists it, also not with `CARD_TYPE((u16)id)`.
- Loop 2 has no explicit pointer increment: it computes a per-iteration address in `ZB2` order (`p*0xD64 + j*0x94 + base`). Pass 1 hoists only 1, the `&`, 0xD64 and the multiply; pass 2 hoists 0x94, the base and 2 and strength-reduces the address, which gives the ROM's preheader order `1, &, D64, mul, ldr base, mov #2, add, 0x2E4, add`.
- FAKEMATCH: `z` and `id` then had swapped registers, because `id` (5 refs, live 12) outranked `z` (3 refs, live 9) in global-alloc priority. An empty `asm("" : : "r"(z));` after the id load adds a reference to `z`, so `z` is allocated first and gets r1 (`id` r3), as in the ROM.
- loop.c facts confirmed against `gcc/loop.c`: `threshold = (has_call ? 1 : 2) * (1 + n_non_fixed_regs)` (26 here); a movable moves if `threshold * savings * lifetime >= insn_count` (doubled if it already moved once), and the threshold drops by 3 after every moved insn.
- Failed: the explicit pointer increment in loop 2; the array form `&gDuelZones[1 & i].zones[j]` (both loops strength-reduced); base-first sums (42); an integer-constant base `0x0201930C` (53); register pins on `z` (12).

## Wave 3 matches (2026-10-01/02)

Working notes: `build/wf/EffectTailorOfTheFickleChainB/NOTES.md` (RTL dumps `f.flow`, `f.greg`, `f.lreg` in the same folder).

### `EffectTailorOfTheFickleChainB` (0x1E4, start score 115; FAKEMATCH)

- Case 3 registers (`p` r8, `zn` r5, `tp` r7, `tz` r4): `u32 p`, `int zn`, then `u8 tp = ref->targets[0]` (a `u8` local, as in `EffectTailorOfTheFickleResolve`) and `int tz = ref->targets[0] >> 8`. With `int tp = ((u8 *)ref)[0xC]`, `tp` and `p` swap r7/r8 (global-alloc priorities 3/15 versus 8/37).
- Case 3 compare: `u32 a = p << 24; u32 b = (u32)zn << 24; r != (u16)((a >> 8 | b) >> 16)` with `r` the `FindMonsterLinkedToCard` result gives the ROM's `lsl, lsl, lsr` order (the `0x08040110` form).
- Case 2: `const char *fmt = gStrDesignateMonsterToSwitchEquipFmt;` declared first loads r1 before everything else; `int pl = 1 & ref->targets[0];` before `ZB(pl, targets[0] >> 8)` gives the AND-first, zone-first multiply order.
- FAKEMATCH (reload rotation): the ROM's case-2 increment uses r4, probably because its table/base adds were reloads in r2/r3. Reproduced by pinning the name table to r3 (`register const char *names asm("r3")`) and reading uninitialised `register int k2 asm("r2"), k3 asm("r3")` in an empty `asm("" : : "r"(k2), "r"(k3))` after `(*st)++`. With r2/r3 busy, reload picks r4, and the rotation then gives case 3's constants r2/r3/r4 as in the ROM. Pinning the step pointer itself to r4 also gave r4, but its r4 preference swapped `tz`/`zn` in case 3.
- Cross-jump direction: the ROM merges case 3's increment into case 0's (`_080402E6`). With `(*st)++; return 0;` in case 3, case 0 merged into case 3 (candidates are tried latest first). Case 3 is now `if (keys) { ...; if (ok) { TryAddEffectTarget(..); (*st)++; goto out3; } PlaySE(3); } out3: return 0;`: the success jump first targets `out3` and is only later threaded to the return, so case 0's copy survives. A `goto inc` into case 0 also matched.
- Failed: a fully break-style switch (256); case-2 variants without the pins (24-32). Open idea for a cleaner form: ordinary C that leaves the base/table constants unallocated, so that reload rematerialises them in r2/r3 and the increment gets r4 naturally. See [[matching-tricks#Register allocation priority and reload rotation]].
