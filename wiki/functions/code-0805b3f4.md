## Matching tricks learned

- **Bit-field clears as halfwords:** `x.b = 0` on a `u16 a:2; u16 b:8; u16 c:6;` bit-field inside a 4-byte struct gives `ldrh; and (ldr =0xFFFFFC03); strh` with the exact int mask. Plain `&= ~0x3FC` on a `u16` narrows the mask to `0xFC03` and does not match (`sub_0805BB80`).
- Clearing bit 0 of a `u8` with a one-bit bit-field gives the `mov r0,#2; neg r0,r0; and` (-2) mask the ROM uses (`sub_0805BC24`).
- A `switch` with `default:` that returns, placed first, produces the ROM's `cmp #n; bls; b <default>` head and the `mov pc, r0` jump table; cases that share a body (`case 1: case 3:`) share a table entry.
- `if (x != -1) break; continue;` versus `if (x == -1) continue; break;` flips the branch sense of the tail (`beq` vs `bne`); use the former when the ROM has `beq <continue>; b <check>`.
- A loop reading `gUnk_0201A070[j]` through a cast integer pointer (`(struct DuelZone *)0x0201A070`) reloads the base on each use; through the extern it is hoisted (`sub_0805BC24` case 4).
- `sub_08047114` has to be prototyped `int` for `sub_0805B3F4` (no `lsl/lsr 16` before `cmp`) but the caller `sub_0805B884` casts the result to `u16`.
- Uninitialised local used as accumulator lands in `r8`/`r9` exactly like the ROM (`sum += info.value` in `sub_0805BC24` case 4 never initialises it: an original bug).
