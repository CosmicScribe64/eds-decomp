## Structs and globals
- `0x0201CFB0` duel screen: `+0x830` byte (bit 0 = "animating"), `+0x834` player, `+0x835` zone, `+0x836` halfword (low byte flag, high byte row), `+0x838` step, `+0x839` frame counter.
- `0x0201D7E4` pick/animation block: `+0` word, `+4` step, `+6/+8` s16 x/y offsets, `+0xC`/`+0x10` packed positions `{u32 f0:1, f1:4, f2:9, rest:18}` (args of `GetAreaX`/`GetAreaY`, which turn a packed position into screen x/y), `+0x1E` halfword. In the ROM the literal is `0x0201D7F0` (the first packed word); the other fields are addressed relative to it.
- `0x03000040+0x4862` u16: copy of VCOUNT for the HBlank effect; `0x02018450+0x15D` u8: table row. That is the same byte as the transition sub-step of [[code-0805e788]] (`struct ScnE788`, `+0x15D`); `BattleScene_Init` sets it to 0 before installing the HBlank handler.

## Matching tricks
- **Bitfield words must be read through their own 4-byte struct** (`*(struct PickBits *)&gDuelAnimArgs.bits`): a bitfield inside the big struct gives `ldrb`/`ldrh` pieces, a 4-byte struct gives `ldr` + `lsl/lsr`.
- **Symbol-relative constants:** addresses `sym + N` are derived from a literal already in a register (`adds r4, r5, #0; subs r4, #8`); locals like `u8 *step = &gUnk.step;` per access reproduce the ROM's explicit address adds, direct field expressions fold the offset into the load.
- **Expression order for sums matters:** `x += a * 0x78; x += 0x47;` (two statements) and `(a << 14) + 0x06004000 + (c << 5)` as separate `+=` statements reproduced the ROM's add order; a single expression was re-associated by gcc.
- **`u16` parameters used only in a zero test** narrow with a single `lsl 16` (`0x0805DF04`); `u16 t` for a multiplier avoided a spill in `0x0805DA1C`.
- Loops of `dst[i]` with hoisted constants (`0x3F`, `0xFC0`): the ip/r8 order of `0x0805DF34` was reproduced in wave 1 with named `u16` mask locals plus integer-address tables (see below).

## Wave 2 matches (2026-10-01)

Working notes: `build/wf/BattleScene_SetCardArtMap/NOTES.md`.

### `BattleScene_SetCardArtMap` (0xD0, start score 57; ordinary C)

- The parked draft hand-wrote shifted accumulators (`t = h << 24`, `u = t + 0x1000000`). The ROM's `lsr rX, r3, #24` values are in fact loop.c strength-reduced givs of a plain `int` counter: `(u8)v` is `(v << 24) >> 24`, so `v << 24` and `(v + 1) << 24` become givs. Giv increments are pseudos that loop.c creates after CSE, so they are never merged with the biv's own `+= 0x2000000` constant. That is why the ROM rematerialises the constant for one add and keeps a hoisted register for the other.
- What matched: an `int` counter with `(u8)v | (u8)(v + 1) << 8` stores (117 -> 60, right constants). Then the inner loop `for (j = 0; j < 4; j++)` with indexed stores `p[j]` / `dst[j]` (`p = dst + 1` in the odd branch), so that the store pointer becomes a giv too and the insn order matches (score 4). Finally, `v /= 2` in place of a new local `c = v / 2` fixed the division temporary's register (r0 vs r3) -> 0. The row loop is a plain `for (row = 0; row < 10; row++) { ...; dst += 16; }`.
- Failed: `dst[j + 1]` and `(dst + 1)[j]` gave `[r4, #2]` addressing (8).

### `DuelAnim_UpdateFlip` (0x140, start score 104; FAKEMATCH)

The score went 104 -> 128 -> 78 -> 72 -> 56 -> 22 -> 20 -> 0.
- `struct ScrFlags *sc` with `struct Sel *q = &sc->sel` and `u8 *step = &sc->step` keeps the base in r8 (base+0x834 / +0x838 / +0x839). Case 1 reads `gDuelScreen.cnt` directly, which gives the ROM's fresh literal + 0x839.
- Card word: `((struct Side708 *)gDuelZones)[pl & 1].z[zone].w` gives `((pl&1)*0xD64 + base) + zone*0x94`.
- Frame table: a real 2D extern alias `gAnimFrames_081A4474[][24]` gives the `(cnt*2 + row*48) + base` order. A cast pointer to an array becomes pointer arithmetic, which gives the wrong order.
- `flag ? 0x1000020 : 0x1000000` inline in the call gives the ROM's argument order; an `if` before the call computes that value first.
- Bit 12: `attr &= 0xEFFF;` in place, then `int k = call + 0x1000; int s = (s16)attr + k; attr = s;`. The `int` temporary stops convert_to_integer from narrowing away the `(s16)` extension, and the separate `k` stops fold from reassociating to `(attr + 0x1000) + call`.
- pl/zone r6/r7 swap: FAKEMATCH `gAnimFrames_081A4474[pl = row][cnt]`, from the permuter. Reusing pl as the row index (row <= 0xFF) keeps pl live past the second call, which puts pl in r7 and zone in r6. The NOTES record a cleaner alternative, not applied, that also matched in the working copy: load zone through an `int` temporary (`int z; z = q->zone; zone = z;`) with a plain `[row]` index, the trick that `DuelAnim_UpdateChangePosition` uses. It is a candidate for a cleanup pass (`wf.py prep` refuses functions that already match).

### `DuelAnim_UpdateChangePosition` (0x17C, start score 173; ordinary C)

Rewritten from the matched `DuelAnim_UpdateFlip` shape (173 -> 48 -> 32 -> 20 -> 0):
- It keeps the same sc/q/step pointer locals, 2D table aliases (`gAnimFrames_081A4474[][24]`, `gAnimScale_081A44D4[][10]`), in-place `attr &= 0xEFFF` with `int` k/s temporaries, and direct `gDuelScreen.cnt` reads in case 1. `(gDuelScreen.cnt * 24) / 10` reproduces the ROM's double `ldrb` of cnt.
- `int side = pl & 1;` comes first. fb is read through pointer arithmetic with the symbol last, `((struct Zone58C *)(side * 0xD64 + zone * 0x94 + (u32)gDuelZones))->fb`, which loads the base literal after the offset. A global struct-array extern loads the base first (expand_expr's VAR_DECL path). The id uses the `((struct Side58C *)gDuelZones)[side].z[zone].w` form, and CSE shares the terms.
- `attr = tbl[fb][0]; if (row) attr = tbl[fb][...];`, not if/else.
- a and b are declared at function top, before row. a ties row in priority (2 refs / 49) and wins on the lower pseudo number, so a gets `sl` and row is spilled, as in the ROM.
- pl/zone swap (live length pl 61, zone 62): `int z; z = q->zone; zone = z;` adds a narrowing insn before combine. That makes zone's live range one insn shorter, so zone is allocated first (r6) and pl gets r7. Combine then folds the narrowing away. Declaration order does not matter.
- Failed: a `u16` third-parameter cast for `GetAreaX`/`GetAreaY` (adds real moves); the `[pl = fb]` index trick from `DuelAnim_UpdateFlip` (breaks this one); and register pins (`register asm("r7")` reuses the pinned register elsewhere).

### `BattleScene_HBlank` (0x104, start score 108; ordinary C)

- The old draft computed the address by hand as `(H<<2) + K*640 + (u32)table`. The table literal loaded before the IO address, and the sum accumulated in the K*640 register instead of the H*4 register.
- What matched: a real two-dimensional ARRAY_REF, `((const struct WarpTbl32 *)gBattleSceneOpenBgX)->a[K][H]` (a struct holding `u32 a[16][160]`; `u16` for the third table). gcc expands ARRAY_REF chains through get_inner_reference: it expands the base (table address) first, then the offset `H*4 + K*640` (inner index first), and adds the base last. That gives exactly the ROM's order of literal loads and accumulator registers. No FAKEMATCH is needed.
- Failed: a cast to a pointer-to-row type, `((const u32 (*)[160])tbl)[K][H]` (254). The C front end turns `ptr[i]`, and ARRAY_REF on an INDIRECT_REF, into pointer arithmetic `*(p + K*640 + H*4)`, which computes K first and the table last. The struct wrapper is needed because the file-scope externs are 1-D `u32[]`; a member array of a struct gives a true ARRAY_REF.

### `BattleScene_SetCardFrameMap` (0x1E8, start score 222; ordinary C)

- The final source uses the same loop shapes as `BattleScene_SetCardArtMap`. Once the structure was right (score 106 in the NOTES), only register allocation differed: dst was in r6 instead of r7, the loop-1 pointer in r5 instead of r6, and the loop-1 counter j in r7 instead of r5.
- Fix: declare `int j` once at function scope and share it between loops 1 and 3 (it had been two block-scoped variables). The merged pseudo has 44 refs over a live length of 116, so its global-alloc priority is 5*44/116 = 1.90. That is above the loop-1 pointer givs (3*11/18 = 1.83) and dst (5*59/171 = 1.73), so j gets r5 first, the pointer r6 and dst r7, as in the original.
- Lesson: when a counter lands in a higher register than the target, check whether the original shared one loop variable across several loops. Merging the pseudos raises the counter's refs and its priority.

### `BattleScene_Init` (0x3D0, no start score recorded; ordinary C)

- The old `s8`-parameter m2c draft scored 214 earlier and no longer compiled, because its prototypes conflicted with the now-matched `BattleScene_LoadCardArt`/`BattleScene_LoadCardFrame`/`BattleScene_SetCardArtMap`, so prep recorded no start score. Rewritten from the asm, it started at 74 and reached 0.
- The parameters are `u16`, and the unit's own definitions of `BattleScene_LoadCardArt`/`E054`/`E100` are not redeclared.
- Bits 1 and 2 of byte 0 of `gDuelScreen` are cleared as two separate 1-bit bitfield stores (`f1 = 0; f2 = 0;` through a struct overlay), which gives the ROM's two ANDs (-3, -5) with a single load and store. A plain `& -3 & -5` folds into one AND.
- `gMain+0x40E` needs a struct member access (`((struct E3B8Main *)&gMain)->f40E = 1`), which emits the ROM's separate base and offset literals plus an `add`. Pointer arithmetic folds them into one literal.
- The portrait choice is a static inline (`E3B8_Portrait`): `switch ((int)CARD_TYPE(id))` for 21/22/23, then a switch on the subtype helper used in [[code-08006878]] / [[code-08007994]] (number 1910 -> 3, 1911/1912 -> 1, then `(u8)type` 22/21/23 -> 7/8/9, else bits 18-19). Subtypes 1/2/3 pick the three frames; anything else gets the default. The `(int)` cast on the outer switch turns `bhi` into the ROM's `bgt`.
- The card tables are integer-address macros (`((const u32 *)0x08621DE0)[id & 0x7FF]`, `((const u16 *)0x08622AB4)[...]`).
