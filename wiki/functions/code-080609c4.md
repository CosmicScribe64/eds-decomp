## Matching tricks

- **Fade steps with `if (x <= N) return 0; ...; return 1;`** give `bls L0` with the body in the fall-through (and let gcc derive `DISPCNT` from the BLDY pointer with `subs r2,#0x54`); the positive form `if (x > N) { ...; return 1; } return 0;` puts the body out of line. For fade out use `if (b != 0) { BLDY; BLDCNT; return 0; } call; return 1;` (`0x08060C68`).
- **Bitfield byte with 6-bit level** (`u8 brightness : 6;` inside a big `struct Main`) reproduces `ldrb; lsl 26; lsr 26` and the `bic` of the upper bits in `+=` / `-=`.
- **`return FadeToBlack(4) != 0` shapes**: `if (x != 0) { f(); return 1; } return 0;` matches `0x08060B4C`.
- **`AddSprite(0x00400058, 0x40C0, t |= 0x6000)`** (compound assignment inside the argument) loads the constant args first and keeps `t` in r3 (`0x080617F8`).
- **Helpers called through `int` asm-name prototypes** (`void f_i(s32, s32) asm("ClearTileBlock4x4")`) so that callers do not narrow the `u16` parameters of the real definition (`0x08060ECC`, `0x08061004`).
- **Explicit 4x4 block stores** `p[0] = t++; ... p[0x63] = t;` reproduce the unrolled halfword stores; `p = gUnk_03001C5C + (x + (y << 5))` for `u16 x, y`.
- **Explicit coordinate narrowing** (`0x08060E2C`): `u32 x, y` parameters with `(u16)x` and `(u16)y` at index formation reproduce the target's early tile-parameter narrowing. The three-register calling convention and low-half coordinate behaviour are unchanged.
- **2-D table access** `gDuelZonePositions[player][zone].x / 8` gives the two separate shifts (`zone << 3`, `player << 7`) and the signed-divide fix-up.
- **Sequence the decomposition of packed args at the point of use** (`0x0806120C`): `p2 = b; z2 = b >> 8;` between the two helper-call pairs, and `x |= y << 16` just before the tile computation.

## Screen-init loop match (2026-10-01)

`DuelScreen_Init` matches all 0xE8 bytes with one initialized r3 binding for the u16 base tile 0x4280 and no empty constraints. Initialize i, the first destination, tile, then the second destination. Stage the first halfword as `*a = i; *a += tile;`, leaving `*b = tile + i;`. The compiler forwards the value and emits exactly one store to each destination, with the target's operand order. For the two iterations, i is 0/1 and both destinations receive 0x4280/0x4281; pointers address distinct halfword arrays. Removing the tile binding or replacing it with a wide integer changes scheduling.

The bounded one-worker permuter found this defined rewrite at iteration 855 (17 compile errors), from a one-byte miss. No uninitialized values, dead branches, invented ABI or extra runtime stores are used. The final whole-unit check and full-ROM checkpoint 24 pass. Evidence: `build/bigguns-lead2/screen_init_*.py`, `enable_screen.py`, `screen-permuter.log`, `DuelScreen_Init/solo-clean/`. Earlier scheduling limitations above are superseded.

### `DrawFieldOverlay` (0x150, start score 64; ordinary C)

Score 64 -> 0 in about ten experiments.
- r8/r9/sl saves and hoisting: the player-state field is read as `((struct PS580 *)((u8 *)&gDuel + 4))[idx].u26` and the `+0x1B12` flags through a cast pointer `((struct DuelGlobals *)&gDuel)->f1B12_x`. The `0x1B12` address is then `sym + 0x1B12` in two literals, CSE derives `sym + 4` from the symbol register (`adds r2,#4`) and loop.c hoists it into r9; the frame counter is no longer hoisted. A plain `(u8 *)g + 4 + idx*0xD64 + 0x26` folds to `+0x2A`.
- Zone address: `(1 & p) * 0xD64 + zn * 0x94 + (u32)gDuelZones`, with the player term written first, gives the ROM's `z*0x94`-before-`p*0xD64` order; the `ZB()`/`ZB3()`/array-index forms did not.
- `u32 x` (not `u16`) and `y <<= 16; x |= y;` as separate statements keep the OR result in x's register (r4); `x |= y << 16` put it straight in r0 (41), `x = (x+8) | ((y+8) << 16)` gave 14.

### `DrawAreaTiles` (0x1A8, start score 30; FAKEMATCH)

The starting draft (score 30) had been parked by an earlier `wf.py` attempt; the original goto draft scored 321 by the wave 3 agent's measure.
1. Every case is `if (count != 0) { ...draw... } else { clear }`. Cross-jumping then keeps the ROM's tails: 0x1230 stays in case 12, the clear in case 14, 0x1070 and the draw in case 15, and case 15's own clear goes at the end.
2. A private 0xD64-byte view `struct PlayerState_08061004` through the address-suffixed extern `gPS1004_020192E4` (asm-name aliases are rejected by `wf.py apply`), with direct `PS04[1 & player].field` accesses and no `ps` pointer, so the base is loaded first.
3. List element (FAKEMATCH): `list = PS04[i].a904; o = PS04[i].b4 * 4 - 4; list = (u32 *)((u8 *)list + o);`. `list[b4 - 1]` and every other pointer form give `lsl; add; sub #4`, because `pointer_int_sum` and the `EXPAND_SUM` distribution move the -4 outward; an ARRAY_REF gives `sub; lsl`. Only a separate byte-offset variable gives the ROM's `lsl; sub; add`, and assigning back to `list` makes the sum reuse its register.
4. `list`/`o` are declared inside each case block; shared function-scope variables become global pseudos and put `base + 0x904/0xB84` in r0 instead of r1.
5. Case 14 passes `(u16)(GetCardIconBgTile(...) + 0x2000)` straight to the call, which gives `adds r2, r0, #0` with the add done in r2.
6. Case 15 needs two calls, `if (cc == 2) draw(x, y, 0x1070); else draw(x, y, t);`. This adds one ref each to x and y, which lifts x above the case-15 offset in global-alloc priority (x r5, offset r6, y r7); with `t = 0x1070; draw(t)` r5/r6 were swapped. The machine code is the same after cross-jumping.
- All calls go through the unit's `_i` int-parameter aliases; mixing in the real (u16) `FillTileBlock4x4` prototype stops cross-jumping, because the two symbol_refs differ.
