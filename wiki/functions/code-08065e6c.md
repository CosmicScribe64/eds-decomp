## Matching tricks learned (old_agbcc)

- **Two locals instead of one**: `sub_08066478` only matched after the first (`if x != 0xFFFF`) block used its own pointer `t` and the loop used a separate `e`; with one shared pointer gcc assigned the shift temp to `r0`. Same for any "same pointer, two live ranges" mismatch.
- **Add operand order** `i * 16 + (u32)p` versus `(u32)p + (i << 4)` flips which operand is the base in `adds`: `sub_08066244` needs `(u32)p + (i << 4) + 0xC`, `sub_080665D4` needs `i * 16 + (u32)p`.
- **`a - 4 - f()`** is re-associated to `a - (f() + 4)` by gcc; write `t = f(); z = a - 4; z -= t;` (`sub_08065F78`).
- **Sums fold differently**: `(y + 0xC) + x` needs a named temporary `yy = y + 0xC;` to keep the order.
- **Stack-heavy calls**: `sub_0807B6B8` takes 13 arguments (4 in registers, 9 on the stack; the last is `&gUnk_0201DB20`). A missing 13th argument shows up as a 4-byte smaller frame.
- **`x && y` conditions**: `if (x != 0 && b > 3) { A } else if (b <= 3) { B }` produces the target's shared tail; two nested `if`s with a duplicated block do not.
- **Constants not folded**: a literal `0xA000` vs the target's `movs #0xA0; lsls #7` = `0x5000`; always convert `lsl` immediates back to numbers.
- **Large offsets on an extern struct** (`gUnk_0201DB20_c.f18B2`) give the two-literal `ldr r1,=0x18B2; adds r0,r4,r1` form; a `(u8 *)&sym + 0x18B2` cast folds into one literal.
- **Card "kind" in this page is the stats type field** (bits 20-24 of [[card-table]]): `0x15` Trap, `0x16` Magic, `0x17` Ticket, `0x18` Divine; the `stats >> 18 & 3` value is the monster kind (normal/effect/fusion/ritual).
- **agbcc rounds struct sizes up to multiples of 4**, also for members of a `union` (see [[code-08068180]]).
- **Unusual parameters**: `sub_08066478` has an unused third parameter (param regs are still narrowed in place). `sub_0806635C` is called with 1 argument by `sub_08066478` but the caller `sub_0806664C` passes five registers/stack words that the callee ignores (unresolved, see below).
- **`volatile`/`s16` reload tricks did not produce `ldrsh [r0, r1]`** (`sub_08066260`): the store to `o[0]` is forwarded to the following load; the target keeps the reload.
