# Unit duel_cmd_field

The unit covers `0x0800D8A4`-`0x0800EAA7` (Thumb, `old_agbcc -O2`), and its source is `src/duel_cmd_field.c`.
It holds nine duel script-command handlers, dispatched by `DuelCmd_Dispatch`. Each runs as a small multi-frame state machine on the command block `gDuelCmd`. `step` is `+0x80A` bits 0-6, incremented per stage, and `running` is `+0x80D` bit 5, cleared when the command finishes. The command arguments are `hdr` (`+0`, bit 15 = acting player), `arg1` (`+2`, zone index) and `arg2` (`+4`).

The unit status is `unit bytes MATCH` (`tools/check.py duel_cmd_field`, built and target both `0x1204`), with **7/9 functions in C** (`DuelCmd_ChangePosition`, `DuelCmd_FlipCard`, `DuelCmd_SendToGraveyard`, `DuelCmd_Banish`, `DuelCmd_BanishFlagged`, `DuelCmd_ReturnToHand`, `DuelCmd_ReturnToDeck`), covering `0xD8C` bytes. Two functions retain drafts under `#if 0 /* NONMATCHING */`. Those drafts are starting references, not verified semantic equivalents. The September 30 reconstruction found semantic errors as well as register and stack differences in the earlier DA84 draft.

The unit includes `include/duel.h` and not `main.h`, because it never uses `gMain`. Its local definitions of `DuelCard`, `DuelZone`, `DuelPlayer`, `DuelState` and `DuelZones` and its local `extern` declarations of `gDuel` / `gDuelZones` were removed in favour of the canonical header. Field accesses were remapped by offset: `zone->faceDown` became `zone->flag6_0`, and `struct DuelZones` became `struct DuelZonesPlayer`. A new local `ZoneFlags18` byte view exposes card-word bit 18 for DA84 without changing the shared header, and DA84's byte bitfield clear needs it.

## Structs (hypotheses, from the attempts)
- Unit-local only (kept, not in the shared headers): `gDuelCmd` = `struct DuelCmd` (`+0 u16 hdr`, `+2 u16 arg1`, `+4 u16 arg2`, `+0x80A` byte: bits 0-6 `step`; `+0x80D` bit 5 `running`; `+0x814` a `struct DuelCard` scratch word), and `struct CardLoc` (u16 bitfield: player:1, area:4, slot:9, flag14:1, flag15:1).
- Shared `duel.h` (remapped during header migration): `DuelCard`, `DuelZone` (0x94 bytes, `+0` card word id bits 0-11, `+4` u16 `serial`, `+6` bit 0 `flag6_0`, bit 1 `flag6_1`), `DuelPlayer`, `DuelState`, `DuelZonesPlayer`; `gDuelZones` = `&players[0].zones[0]`. Zone address is `0x0201930C + player*0xD64 + slot*0x94`. See [[duel-piles-c]].
- `gDuel` (`0x020192E0`): `+0 u16 serial` counter (canonical header names it `unk0`; the unit only touches it as raw `gDuelZones - 0x2C` byte arithmetic, so no rename was needed).

## Matching notes
- `DuelCmd_ChangePosition` and `DuelCmd_FlipCard` match except for one register swap. The ROM has `player` in r4 (r5 for `D990`) and `slot` in r5 (r6), and the compiler produces them the other way round. `player` and `slot` have equal reference counts. None of these change the result: declaration order, `u16`/`u32`/`u8` types, reading `slot` before `player`, per-use zone recomputation, extra references. **Workaround that matches `DuelCmd_ChangePosition`:** `register u32 slot asm("r5") = gCmd.arg1;`. Forcing only `slot` works, while forcing both or only `player` breaks it. **`DuelCmd_FlipCard` (solved):** `register u32 slot asm("r6")` alone still left the register-asm slot copy in the `slot*0x94` multiply. Decoupling the products into named locals **and** pinning `zones` to `r1` fixes everything: `u32 off = 0x94 * slot; struct DuelZone *zone = (u8*)zones + off; off += player*0xD64;` then read the card id through `(u8*)gDuelZones + off`. Writing `off += player*0xD64` (instead of a fresh `idOff`) makes the ROM's `adds r0,r0,r2; adds r0,r0,r7` accumulator, and `register struct DuelZonesPlayer *zones asm("r1")` puts the player-product in r2 and the address in r1. The zone pointer form that matches the address arithmetic is `struct DuelZones *zones = &gDuelZones[player]; zone = &zones->zones[slot];` (the `ZONE()` byte-arithmetic macro gives a different add order here).
- `DuelAnim_Request`'s argument `((u8)slot << 8 | player) | (fd << 16 | b)` reproduces the ROM's shift order when `u32 fd = zone->faceDown; u32 b = arg << 24;` are separate locals.
- `DuelCmd_FlipCard` addresses the serial stamp from the zone base. `(*(u16 *)((u8 *)gDuelZones - 0x2C))++` gives the ROM's `sub r0,r7,#0x2C`, and using `gDuel.serial` does not.
- `DuelCmd_SendToGraveyard` and `DuelCmd_Banish` match in ordinary C with no fixed registers or assembly hints. Declare `from` and `to` once before the switch. The same `from` object is passed to `DuelAnim_PlayZoneEffect` in case 1 and rewritten in case 2; its escaped address makes the later stores byte/halfword accesses instead of the first case's word stores. Independent per-case locals fail this layout.
- Delay case 1's zone pointer until after `from.player`, `from.area`, and `from.slot` stores. Stage `pp = player & 1`, then use zone-first integer stride arithmetic. In case 2, initialize the saved-card pointer, player offset, `zonebase = base + poff`, and zone offset in that order. The copy uses `zonebase + zoff`; subsequent zone access recomputes `zoff + poff + base`. A single cached zone pointer loses the ROM's distinct calculations.
- Keep the saved ID as `u32 id = (word << 20) >> 20`, read the card-number table through `CARD_NUMBER(id)` (absolute-address macro), and extract the owner using `(word << 19) >> 31`. Direct named-table indexing schedules the literal too early; `(word >> 12) & 1` adds a redundant mask. Use the global command reference for the default completion to reproduce its base reload.
- DA84's card bit-18 clear uses the local `ZoneFlags18` byte bitfield. A raw `byte &= ~4` becomes `mov #251`; the bitfield gives the observed `mov #5; neg` and recovers the final two-byte instruction difference. Both complete units were checked after acceptance. DA84 contributes `0x280` new matching C bytes and DD04 `0x290`.

## Parked drafts (listed functions)
Two functions remain as unverified drafts. Check their semantics and stack-object lifetimes against ROM before treating them as allocation-only near misses.
- **Historical DD04 failure:** pinning player/slot matched the prologue but did not fix shared-stack lifetime or address staging; private isolated compiles also produced unsuitable slot-register uses. The accepted reconstruction removes both pins and resolves those differences through ordinary C.
- **Historical `DuelCmd_BanishFlagged` and `DuelCmd_ReturnToHand`**, plus the remaining **`DuelCmd_MoveToZone`** (an `if`-chain). The step must be read from `u32 step = gCmd.step;`, because direct `gCmd.step` comparisons give `and #0x7F` instead of the ROM's `lsls/lsrs`. Register allocation differs. For `E1E0`, `register u32 player asm("r6")` and `register u32 slot asm("r7")` come close. For `E630` the ROM keeps `c` and `d` on the stack (frame 0x24).
- **`DuelCmd_SwapZones`**: structure is right (step 0 checks two zones, step 1 `DuelAnim_SwapCards`, step 2 three `MemCopy16`); only register allocation/stack layout differ (ROM: base r9, `a` r7, `b` r8, `c` sl, `d` at sp+0x9C).
- Common to both: `arg1`/`arg2` in these two-zone handlers are `(player \| slot << 8)`; the zone base is `gDuelZones` and `ZB(p,z) = z*0x94 + p*0xD64`, `ZONE(p,s) = p*0xD64 + s*0x94`. `CopyDuelCard(dst, src)` copies a card; `CopyDuelCard(&zoneC->card, &gCmd.saved814)` in `E630` writes the saved card into the destination zone.

## September 30 sibling batch (two more exact conversions)

Both `DuelCmd_BanishFlagged` (`0x24C`) and `DuelCmd_ReturnToDeck` (`0x1F8`) were accepted in ordinary C, with no fixed registers or empty assembly hints. That adds 2 functions and `0x444` bytes. Strict whole-unit checks after both activations produced `0x1204` bytes **MATCH**, including all six active C bodies and three assembly fallbacks. Logs: `build/decomp_large/d8a4-df94-accepted.log` and `build/decomp_large/d8a4-e438-accepted.log`.

- DF94 reuses the escaped `from` stack object between stages, as DA84/DD04 do. Case 1 stores the location's player/area/slot before forming the zone pointer. Use implicit bitfield narrowing for `from.player` and the two flags; spelling extra `& step` masks adds instructions. Case 2 computes the zone-first integer sum, sets zone byte 2 bit 4 **before** saving the card, then uses a differently associated source address for the save copy. Separate case-0 `zoff` and `poff` locals preserve multiplication order. Computing case-2 `zoneoff = zoff + poff` **before declaring the zone base** prevents an extra reload from `ip`, resolving the last four-byte surplus. The destination area is 15, player comes from the command header, and animation is unconditional.
- E438 uses the staged saved-card pointer, player product, zone base, and zone product. The local `ZoneFlags18` bitfield clear preserves `mov #5; neg`; a raw byte mask instead emits `mov #251`. For the card-number lookup, the unsigned byte offset `((word << 21) >> 20)` is exactly `2 * (word & 0x7FF)` and reproduces the ROM's two shifts without a pooled mask. The `IsFusionMonster` argument uses a **fresh halfword read**, `((u32)*(u16 *)saved << 20) >> 20`, rather than reusing the saved word local. This preserves the observed load width and timing. Default-stage completion retains the command pointer; the step-1 increment uses the direct global reference.

E438's earlier table description incorrectly assigned default-stage helper calls to step 1 and the save/animation to step 2. The accepted ROM-exact C resolves that contradiction. The save is command scratch **from** the zone, the bit-18 clear follows the save, and the animation range is based on mapped card numbers, not the raw ID.

### E1E0 acceptance

`DuelCmd_ReturnToHand` now matches all **`0x258` bytes**. The complete unit remains `0x1204` bytes **MATCH**, with **7/9 C functions (`0xD8C` bytes)** and two assembly fallbacks (`0x478` bytes). Acceptance log: `build/decomp_large/d8a4-e1e0-accepted.log`.

The final six differing bytes came from the source expression's multiplication order. The zone-first integer sum made the compiler emit the player multiplication first. Writing the final address as `(player & 1) * 0xD64 + slot * 0x94 + (u32)gDuelZones` instead produces the ROM's **slot multiplication first**. A byte-pointer base-first form and two further associated sums also match; changing signedness alone did not. This is a register-allocation result for this function, not a general claim that source operand order predicts instruction order.

The initialized `register u8 *players asm("r1") = base - 0x28` binding remains necessary to keep the hand-count base in `r1` while the saved owner is read into `r0`. Its empty input constraint was tested and **removed**; the whole unit still matches. Removing the binding leaves nine differing operand bytes. The accepted function has **one initialized register binding, no emitted inline instructions, and no empty barriers**. All other player/slot pins are absent. Its two card-kind calls retain their fresh `u16` saved-card reads, and the destination slot is merged into one assignment after the branch, as documented above.

Private evidence: `build/decomp_large/game-batch/DuelCmd_ReturnToHand/sum-player-first/check.txt`, `min-no-constraint/check.txt`, and grids `zone_e1e0_sumtypes.py` / `zone_e1e0_minimize.py`. The fresh dependency grid did not match and was rejected. No prior failed grid was rerun unchanged.

E630 received eight fresh ROM-reviewed reconstruction variants after the signed16-offset lead: separate destination/source offsets and bases, a recomputed destination address after clear, the byte-7 bitfield clear (`mov #5; neg`), and shifted fresh saved ID. None match. Signed16 masked-player offsets recover `0x240` against target `0x244`, but still miss 561 bytes; cached-step explicit masks and stack-scope variants are worse. These are isolated evidence only, not accepted drafts or conversion counts. Original active fallback remains intact.
